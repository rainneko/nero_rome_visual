# 09 · 多 agent 协作

## 1. 角色
| 角色 | 典型担任者 | 输入 | 输出 |
|---|---|---|---|
| 导演 | 作者；可由顶级模型（如 Claude Fable）代理 | 截图、方案 | 拍板、优先级、审美意见、故事事实 |
| 主建造 | Claude Opus | 圣经、地点表、参考图、意见 | 代码、截图、任务清单、核实记录 |
| 史学顾问 | 另一家的模型（如 Gemini） | 方案和截图 | 时代错误、复原建议、量级（必须带出处） |
| 文本编辑 | 小说编剧 agent | 全书 | 场景—资产文档：原句、章节、状态、史/书中标签 |
| 建模工人 | Haiku 子代理 + Blender MCP | 任务书 | 四机位渲染、GLB、报告 |

**谁来建模：** 英雄建筑、人像雕塑、凡是依赖所在地形的，交给最强的模型；用积木库搭的方盒类小物件、任务书很严的，可以交给小模型。总监不得把工人的"未运行"改写成"通过"（`10-pitfalls.md` #47）。

## 2. 交接文件（单一事实来源）
`bible.md` · `places.csv` · `states.json` · `refs/manifest.csv` · `briefs/*.md` · 链接审批表 · 任务清单（含 [PENDING]/[COMPLETED]）。

## 3. 核实协议
- 每条外来意见都填一行：说法 · 出处 · 主建造核实结果（采纳 / 部分采纳 / 不采纳）· 理由。
- 例 1（不采纳）：顾问说某开源列表里有四个城建项目，核对原文后都不存在。
- 例 2（采纳）：顾问批评夜景太像现代城市，改成稀疏油灯、暗外墙、亮内院后，作者认可。
- 例 3（部分采纳）：顾问给出水景墙"宽百米、高 15 米"，查不到出处，只当作设计选择。
- 作者的原则："不用全信，但是必要的需要采纳。"

## 4. 节奏
- 一轮 = 计划 → 改 → 构建 → 启动测试 → 截图 → 对照 → 报告（做了什么、看到了什么、**还没确认什么**）。
- 工具额度有限时，先做能验证的小步，不要一轮堆十个改动而没有截图。
- 报告里诚实写差距：例"实时程序化渲染离参考图的手绘密度还很远"。

## 5. 主控 + 工人（建模）
见 `06-hero-assets.md` 第 4 节。修改清单要编号、具体、可检查（"塔顶铁矛加粗到 0.2 米、在天空背景下可见"），不要写"再精致一点"。

## 6. Haiku 工人的实际表现（安齐奥，6 个并行）
- 一个工人一份任务书，6 个同时跑，各 15–30 分钟交第一版；大多数一轮修改就过，个别一次过。
- 它们会主动报"我的理解"（例如"塔高 20 米指墙高还是含屋顶"），主控逐条回"接受/改成…"，比事后返工便宜。
- 修改清单要**指认图里的位置**（"west.png 底部两块沙色梯形"），并给出数值界限（"外撇 ≤0.4 米"）。
- 同一个问题在多个工人那里重复出现时，说明是积木库的默认值不对：直接改库，比逐个发清单快。
- 干得好的工人可以续派新任务（翼楼做完后接着做营房），它已经熟悉规范。
- 主控自己负责**地形、分区、放置、场景截图**——工人只看得到单个资产，看不到它和悬崖、台地、别的建筑的关系。

> 成本复盘：Haiku 续用老工人做小修最贵，修改轮请新开工人；详见 [15-token-cost](15-token-cost.md)。

## 7. 分支与交接
- **一个会话一个分支。** 交接前提交并推送；没推送的工作等于没做。
- **"已合并"只按 `git merge-base --is-ancestor <分支> main` 的结果写。** 例：一个带 7 个提交（15 种新房型）的分支躺了几天，清单却写"已合"，因为引用的是 main 合进分支的那个提交（`10-pitfalls.md` #53）。
- **口头答应的事当场写成清单行。** 例：作者先后 5 次说"先查之前说过的，更新清单再继续"。每个会话开工先读清单，把没收口的项报给作者（#54）。
- 每个工人固定负责的文件；合并顺序写进任务清单。
- 合并只要碰了道路、地形或占地，就重新烘焙，并重跑全城审计。
- 并行的无头 Blender 工人数按机器内存设上限，关闭前先存档；渲染图和会话日志按计划挪到外置存储，本地只留一份小清单（#66）。

## 8. 基线与回归
- 留一份"已知失败"基线（哪些检查本来就挂、为什么）。
- 别的会话合并后检查失败：先二分到引入变化的提交，再判断是代码退化还是期望过时；结论写进任务清单（#55）。
- 汇报不得把"未运行"写成"通过"（#47）。
